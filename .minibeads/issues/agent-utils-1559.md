# Description

[watermelon-full-preview] Owner 081 asked for recovery with less fragile deterministic code and more agent judgement; the lead-approved design is the harness living plan `ai_docs/plans/2026-11-15-restore-recovery-agent-plan.md` (harness repo), building on `ai_docs/plans/2026-11-12-team-restore-protocol.md`. Owner corrections on 2026-11-20 reshaped the agent half: 234 (recovery watches from the start), 235 (one-shot calls in a loop, muse first then claude then codex, "emergency recovery mode"), 242-244 (coordb's harness-local shepherd-v0; the shepherd always starts at boot from its own minimal unit, in parallel with restore, monitoring it), 245 (lane restore is both jobs idempotently; lanes may return before the lead; the coordinator sweeps), 243 (per-team YES = lead running + bridge healthy + handoff acked), 256 (restore stays outside Herdr; a `system > recovery` tab tails the recovery log), 257 (report records missing profile/bypass/effort/session; never rewrite them). Phase plan approved by coordb 2026-11-20: judgement-only one-shots, effects only via `team act`; Rust `team shepherd` loop + standalone wrapper script; no bind/record-repair in boot recovery; bounds 300 s per call, 20 rounds / 120 min, early escalation on two identical no-progress snapshots (configurable).

# Design

- Phase 1 (deterministic half, no agent yet): freeze `agentctl-team-manifest/v1` as a redacted allowlist projection of the status rows DETECT already computes — never raw records (record tokens must not reach an agent brief) — with `record_gaps` (missing profile/bypass/effort/session, ambiguous candidates with first-prompt evidence), queued census, unit booleans, refusals, `lost[]`, `errors[]`, and the embedded `agentctl-team-verify/v1` result. Then `agentctl team act --incident I --request-id R <action>`: validated against the manifest, idempotent per request-id, persisted in the driver record, verify-after, exits 0/75/1. Allowlist v1: facts, revive (recorded session only), start-unit/reset-unit, drain, kill-pid, bridge gap actions wrapping the landed pin-guarded gap verbs, declare-done (a full-VERIFY request), escalate. No `bind-session` and no record-repair writes anywhere in boot recovery (257); candidates are report-only. New persisted data (DriverRecord `manifest`/`actions[]`, shepherd stamp/state files) is reported to coordb before each landing because another team pins an older agentctl reader.
- Phase 2 (shepherd): a standalone `run-agent-prompt` wrapper tries `muse exec`, then `claude -p`, then `codex exec` (stateless, tool-less, hard process-group timeout, distinct all-fail exit 69, logs which harness answered). The shepherd loop starts unconditionally at boot from its own minimal unit in parallel with restore (no ordering on restore or Herdr), polls manifest/verify facts for every team in the restore-teams teams config, and per round accepts at most one own-team `team act` proposal from the one-shot's structured final JSON line. It finishes only on a deterministic YES per team — lead running, bridge healthy, handoff acked, each an explicit pass (held/skipped never count) — including other teams' leads judged read-only, or on bounded give-up with escalation + stamp. If deterministic checks pass with all harnesses down, the stamp still says YES with judge=none. The shepherd unit appears in `services list` and turnover like other agent-utils daemons; watch/turnover defer while an incident is non-HEALTHY. Visibility: per-boot recovery log under `~/.local/state/agentctl/shepherd/<boot-id>/`, best-effort `system > recovery` Herdr tab tailing it (display only).
- Split: #1975 (slot re-attach, sweep-notice wording, longer boot-restore timeout) and #2000 belong to mu-restoreboot; #1934/#1992/#1993 belong to mu-restorefix. This lane consumes their landed outputs and reports absent state; it does not duplicate them.

# Acceptance Criteria

- A human driving `team act` by hand recovers a scratch drill team end to end; duplicate request-id and stale incident are safe refusals/no-ops; held/skipped verify rows can never produce YES.
- Scratch-registry drill with a fake Herdr (`--herdr-bin`) and fake muse/claude/codex executables proves shepherd fallback order, timeout fall-through, deterministic YES/NO, cross-team read-only judging, and record-gap reporting — without a real reboot, restore, or live registry.
- Wrong-conversation safety: ambiguous or missing native sessions refuse with named candidates in both Rust and Python editions (where mu-restorefix has not already landed it); restore/recovery rewrite no records.
- Every liveness/restore/revive change gets a coordb cold review before gating; landings only on coordb LAND NOW; no real restore/reboot drill without coordb's explicit OK.

Revised Phase 2 design check (mu-shepherd, 2026-11-22, OWNER 327; supersedes the implementation in commit `93aa009b` and its gate — neither is to land without a new go):

- Product boundary: everything needed by an outside team ships in the reusable core and its operator docs: the recovery command and loop, profile configuration, install/smoke tooling, an optional boot-unit renderer, the team-restore protocol, and the setup-skill flow. No site-specific script is wrapped or required. A site may choose its trigger, profiles, escalation routes, and optional supervisor, but does not supply recovery logic. When this lands, the harness-local watch-only prototype is retired in favour of the core entry point; migration is "run the core installer, smoke-test profiles, replace the old trigger target, then remove the prototype."
- One trigger-neutral entry point: `agentctl --registry R start-recovery [--foreground] [--wait]`. It is the only supported way to begin a boot/outage incident. It performs bounded preflight (registry readable, required paths mounted, configured executables present, state directory writable), creates or joins the incident, launches deterministic restore and the recovery-agent supervisor concurrently, and returns a versioned JSON result. Default mode returns after both children are safely detached; `--foreground` keeps the supervisor in front for a container process, an interactive operator, or a supervisor that expects the main process to remain alive. A service manager unit, a startup script, a remote shell, and a human all call this same command. The optional unit is a thin caller of it, never the definition of recovery.
- Earliest safe start and prerequisites: callers invoke `start-recovery` as soon as the operating system and the registry filesystem are usable. It does not assume a service manager, a graphical session, a particular container runtime, or site-only tools. In a container it can be the foreground process once its registry volume is mounted. On a service-managed host the optional unit merely makes the same call. If a prerequisite is absent, the result is `BLOCKED_PREREQUISITE` with the missing item named; recovery does not silently wait forever or start a partial restore against an unmounted registry.
- Idempotence and one restorer: an incident is keyed by registry plus restore epoch. The start path makes a short atomic claim/heartbeat update under the team recovery state lock, then releases that lock before any long work. A second call while the heartbeat is live returns the existing incident (`already-running`, exit 75) and starts neither restore nor supervisor. Restore's own replay guard and the driver/team-act request ledgers remain additional one-effect guards. A dead claimant may be superseded only after the configured stale interval and only for the same epoch; takeover is recorded. A live team lead, an active driver/restore for the incident, or a live recovery claim makes the new caller a reporter, not an actor. Locks are never held across network/model calls, restore, sleeps, or action waits.
- Configured harness/model profiles: profiles are a team-level fixed configuration at `REGISTRY/recovery-profiles.toml`, separate from `agents/` and separate from launch `profiles.json`; `--recovery-profiles PATH` may name an alternate file for tests or a read-only installation. Proposed schema `agentctl-recovery-profiles/v1`: an ordered `[[profile]]` list, each with a unique `name`, `harness` (`muse`, `claude`, or `codex` in v1), optional `model`, `effort`, per-attempt `timeout_seconds`, and optional absolute `command`. The order is exactly the order tried; there is no hidden built-in order when a file is present. Without the file, `run-agent-prompt` retains its existing default order for compatibility. A profile may repeat a harness with a different model. Secrets are never stored in this file; credentials remain in each harness's normal environment/store.
- Core profile plumbing: `run-agent-prompt` and the Rust recovery loop consume the same parsed profile list. `run-agent-prompt` gains `--profile-file`, repeated `--profile NAME` selection where useful for testing, and `--list-profiles`; its stderr/result metadata names the winning profile as well as harness/model/effort. A malformed profile file, an unknown harness, a duplicate name, a non-absolute command, or a profile whose smoke result is missing/stale makes model judgement unavailable rather than guessing. The deterministic restore path may still run and report `judge=unavailable`.
- Install and smoke test: installation is a distinct core command, proposed as `agentctl --registry R recovery install [--profile-file PATH] [--write-unit|--no-unit]`, driven by the setup skill's guided questions. The installing agent detects installed harness executables and versions, asks which ordered profiles to use (for example, a local Claude profile followed by a Codex profile), writes the team profile file with private permissions, renders the optional trigger unit without enabling it, and then runs `agentctl --registry R recovery smoke [--profile NAME]` for every profile. Smoke means a real tiny round trip, not `--version`: a fixed harmless prompt requires an exact final JSON marker, exercising executable resolution, authentication, model/effort selection, timeout, output parsing, and the profile's ability to produce the structured response shape. A chain smoke also proves that an intentionally unavailable first profile falls through to the next. Results are recorded in versioned state (`install-smoke.json`: schema, timestamp, profile name/harness, executable version where reported, requested/observed model and effort, duration, status, and bounded error class; no prompt, answer, token, or secret). Installation reports done only when every configured profile either passes its individual smoke or is explicitly marked disabled with a recorded reason; a chain with no passing profile is not "installed." Smoke can be repeated after a model, credential, executable, or config change; its timestamp/config hash tells the runtime whether judgement is currently trusted.
- Topology: the supported default places the registry, Herdr, agentctl, and `start-recovery` on the same agents host: the machine/session that can actually inspect panes and revive agents. A separate graphical or virtualised session may be where the owner notices the outage, and separate work machines/containers may hold project execution, but neither changes the control-plane entry point. If the registry and Herdr live on the second machine instead, `start-recovery` runs there; the first machine only invokes it through that machine's normal remote/execution mechanism once filesystems are ready, while claims, state, profiles, logs, and stamps remain beside the registry's state root. A registry on a network share is not a shortcut around this: file-lock and pane control semantics require one owning host. Supporting a split registry/Herdr control plane would be a later explicit design, not an assumption of this landing.
- Runtime states: install states `UNCONFIGURED`, `SMOKE_FAILED`, and `READY`; incident states `CLAIMED`, `STARTING`, `RESTORING`, `SUPERVISING`, `JUDGING`, `ACTING`, `VERIFYING`, `HEALTHY`, `GAVE_UP`, `ESCALATED`, `BLOCKED_PREREQUISITE`, `BLOCKED_PROFILE`, and `READ_ONLY`. The persisted incident state records incident/epoch, owner heartbeat, restore child/report reference, round, last manifest hash, current profile attempt, last action request id, consecutive no-progress count, and terminal verdict. State transitions are persisted atomically before and after effects; a crash therefore repeats at most one idempotent request.
- Loop: each round gathers one manifest/verify snapshot for the owning team and read-only snapshots for any configured peer teams; checks deterministic YES first; performs step 0; calls at most one profile from the ordered chain through `run-agent-prompt`; parses only the final structured proposal; validates and performs at most one `team act` request; then re-gathers facts. The supervisor does not serially wait for restore to finish before watching it: restore and supervision begin together, and the loop interprets partial/restore-replay reports as facts. A judge may propose `facts`, recorded-session `revive`, `start-unit`, `reset-unit`, `drain`, guarded `kill-pid`, `declare-done`, or `escalate`. It cannot bind or invent a session, repair a record, run arbitrary commands/units, or restore a peer team. Repeated proposals for work already requested in the incident are suppressed by deterministic request IDs.
- Stop conditions: stop successfully on deterministic per-team YES — coordinator/lead live, required bridge/unit healthy, and handoff acknowledged, with no required check held, skipped, or failed. Stop as read-only when another owner/lead is live and either report that team's outcome or hand off its facts; do not fight it. Stop and escalate on the configured round/time bound, two identical no-progress snapshots, loss of claim/heartbeat ownership, repeated invalid proposals, or an unrecoverable configuration/prerequisite failure. If every profile is unavailable but deterministic checks pass, finish `HEALTHY` with `judge=none`; if checks do not pass, escalate rather than calling the model forever. Service-manager retry policy must not create a second incident: retries re-enter `start-recovery` and join/report the current claim.
- Reports: every command prints a versioned JSON document and a concise human summary. The incident directory under the agentctl state root holds `state.json`, append-only `recovery.log`, the latest manifest, restore report reference, action receipts, and terminal `stamp.json`. The stamp records verdict, epoch/incident, profile attempts and winning profile/model, rounds, elapsed time, restore outcome, per-check booleans, record gaps, action request IDs, and escalation delivery. Status is queryable without acting (`agentctl --registry R recovery status [--incident ID]`, proposed), and terminal stamps can be queued to the recovered lead and configured escalation routes. No record tokens, prompts, transcripts, credentials, or raw pane text are put in the profile file, stamp, or operator guide examples.
- Documentation and setup deliverables in the same landing: CLI `quickstart`/`userguide` and per-command help for `start-recovery`, `recovery install`, `recovery smoke`, and `recovery status`; profile schema and two worked configurations (a single-profile local setup and a two-profile ordered fallback); service-manager, plain-script/foreground-container, and manual invocation examples; troubleshooting for missing credentials/models, unmounted registry, stale claim, and judge unavailable; and the team-restore skill rewritten around the one entry point. The setup skill asks for the ordered profiles and trigger choice, performs the install/smoke flow, and reports the recorded smoke result. The public recovery guide gets a short link/summary rather than a second protocol.
- Tests: extend the existing scratch drill rather than relying on the superseded gate: profile order is honoured from the file (including Claude-then-Codex with no first built-in harness), individual and chain smoke tests with fake executables, config/install failure cases, `start-recovery` duplicate-call and stale-claim cases, parallel restore+supervisor start, foreground/container mode, no-service-manager manual invocation, optional unit rendering/enable-never-performed, one action per round, read-only live lead/peer teams, deterministic YES/`judge=none`, bounded give-up, and report/stamp fields.

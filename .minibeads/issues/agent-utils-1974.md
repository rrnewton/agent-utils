# Description

[watermelon-full-preview] Owner (240, 2026-11-20): no evidence file-only `chat reply --file` is better for headless. Headless should work basically the same as TUI: assistant text blocks carrying `CHAT_REPLY_NNN` markers are sliced as replies; text outside markers is salvaged to the agent-transcript harvest (#1608 agent-transcripts-timeline). Today #896 (5c78da37) gives headless targets command-only prompts because the bridge "follows no transcript" for headless (`chat_transcript.rs:22-25,167-169`, `chat_runtime.rs:11078-11084`, `chat_service.rs:2099,2118,2130`). Headless is the easy case: its wrapper event log already holds every assistant text block verbatim, with no screen scraping.

# Design

Short design note (WIP, before build; sent to coordb before implementing):

- **Where the event log lives.** `<registry>/agents/<name>/events/<generation>.jsonl` (+ `.<n>` segments, `index.json`), per `rs/agentctl/src/headless/events.rs:8-12,96-100` and `rs/agentctl/src/headless/mod.rs:24`. One JSON line per event: `{v, seq, id, ts (unix ms), agent, generation, session, turn, causation (queue id), type, data}` (`events.rs:53-83`). The wrapper emits `assistant.text` with `data={"text": <verbatim final prose>}` at `rs/agentctl/src/headless/wrapper.rs:1333-1334`, from `Signal::Text` (Claude `rs/agentctl/src/headless/claude.rs:575-586`, Muse `rs/agentctl/src/headless/muse.rs:400`). Thinking/tool calls never become `assistant.text`.
- **How the bridge follows it.** Reuse the existing read-only `headless::events::Follower` (`events.rs:328-412`, `poll()`/`at_end()`), already used by the bridge for approvals (`rs/agentctl/src/chat_service.rs:7649-7650` ApprovalRelay). Add a headless transcript source that implements the same `TranscriptReplies` contract as `CoordinatorTranscript` (`rs/agentctl/src/chat_transcript.rs`, `rs/agentctl/src/chat_runtime.rs:5839-5860`): poll the follower, run `agent_harness::replies::complete_blocks(text)` on each `assistant.text` exactly as the TUI reader does on `Event::Text` (`chat_transcript.rs:493-508`), yielding `TranscriptBlock{identifier, body, at_millis=event.ts}`. In-memory dedup of identical blocks and the 512-block/4MiB caps mirror `chat_transcript.rs:502-515`. No screen is ever read (`ManagedAgents::read_capture` still returns empty for headless, `rs/agentctl/src/subagents.rs:14949-14953`); capture comes from `capture_snapshot*` merging transcript-only blocks (`merge_transcript_blocks`, `chat_runtime.rs:19871-19981`), so an empty rendered snapshot suffices.
- **How a reply is matched to its prompt id.** Exactly as TUI, no new matching: the prompt (now the marker prompt, not command-only) names reply id = alias or `<nonce>_<ordinal>`. `merge_transcript_blocks` maps `block.identifier` via `recognized_reply_marker` to the open request's nonce, requires `at_millis >= answerable_since` (delivered, or delivery-started when uncertain), then `capture_scanned_replies_locked` stores it under the next ordinal. Event `causation`/`turn` are provenance only (they name the wrapper queue item, not the chat nonce) and are not used for routing. `reply_mode()` (`chat_runtime.rs:11078-11105`) must stop returning command-only for headless once this source follows the log; `HEADLESS_EVIDENCE`/resting path in `chat_transcript.rs` and the `reply_source.rs:181-186` early return are updated accordingly. New prompt keeps `chat reply --file` offered as fallback (task 4).
- **Trace / transcript harvest (task 3).** Feed the same follower into the existing trace path, not a duplicate: synthesize `agent_harness::Event::{Prompt,Text,ToolCall,TurnEnd}` from `input.queued/input.started` (prompt excerpt is truncated, so prompt text for `Collector::describe_prompt` comes from the delivered prompt where available; otherwise turn boundaries from `turn.started/turn.completed`, `assistant.text`->Text, `tool.started`->ToolCall) and feed `chat_trace::Collector` (`rs/agentctl/src/chat_trace.rs:583-726`), whose `OutsideBlocks` stripper already removes complete CHAT_REPLY blocks and emits only outside text. The existing trace driver (`spawn_trace_driver`, `chat_service.rs:1032-1399`, `--trace-thread`/`--trace-channel` at 2297-2319) and its persisted high-water/started gate prevent replay; for headless it currently resolves a harness transcript via `for_agent_trace` — switch that source to the event-log source for headless records. #1608's Transcripts view needs no change. Note the harness-support matrix already claims headless trace `supported (typed events)` (`common/docs/agentctl/harness-support-matrix.md:73,437-455`); verify that claim against this source and keep/correct the row in the same commit per AGENTS.md.
- **Duplicates when both a block and a `--file` reply arrive.** Both paths converge on the same store: `chat reply` -> `BridgeState::submit_reply` (`chat_runtime.rs:13450-13546`) and event-log capture -> `capture_scanned_replies_locked` (`chat_runtime.rs:14465ff`), each under `.state.lock`. Whichever arrives first stores the ordinal; the second is suppressed by (a) `KnownReplies`/`ReplyIdentity` text match (`14499-14500`), (b) the stored-bodies `same_rendered_text` check for transcript-only blocks (`14551-14572`), and (c) `submit_reply`'s `stored_ordinal_locked` returning `already_stored` (`13536-13545,13548-13566`). Settled transcript bodies (`settle_transcript_bodies`, `7212-7226`) stop re-adding a settled block. Identity is (request key, reply body), not arrival channel, so ordering (file-first or block-first) does not double-post. A `--file` reply whose body differs from the block text is a distinct reply, as on TUI today.
- **#896 guarantee preserved (task 5).** Delivery receipts are untouched: `with_receipt_when_started(headless||cloud)` (`chat_service.rs:2120`) and queue `message_state` evidence stay as-is; following the event log adds reply capture only, never a delivered receipt without the existing positive evidence (model started, per `rs/agentctl/src/chat_runtime.rs:353,739,949`). If the event log is missing/unreadable, prompts fall back to command-only (the current no-transcript branch of `reply_mode`) — fail-closed, never blocks-without-a-reader.

# Acceptance Criteria

- Headless target gets the marker prompt (`Reply between a line <CHAT_REPLY_NNN> ...`) as TUI does; `reply-path.json`/`chat status` records `blocks`, not `command_only`, while the log is followed, and command-only when it is not.
- A complete CHAT_REPLY block in an `assistant.text` event is stored/sent exactly once, byte-exact (no screen rendering), matched as above; text outside markers never becomes a reply.
- With `--trace-thread`, outside-marker headless text posts to the daily trace thread via the existing Collector/driver and is excluded from replies; CHAT_REPLY bodies never double-post to trace.
- `chat reply --file` still works for headless; same body via both channels posts once (both orders tested); different body posts as a second reply.
- No delivered receipt without existing positive delivery evidence (existing #896 tests still pass).
- Tests: unit tests for the headless transcript source + reply_mode switch; e2e on a TEST bridge with a fixture/scratch channel and scratch headless agent (scratch registry, fake Herdr), never the live owner channel/owner identity/live vibe-talk server. Focused suites `nice -n 10`, `cargo fmt --all -- --check`, then one gate; new test files classified in `validation/components.json`; harness-support-matrix updated in the same commit if a cell changes; no new persisted registry field without telling coordb.

Confirmed (owner 241 via coordb, 2026-11-20): reply mode switches per target and per prompt with NO bridge restart — markers vs `--file` is decided when each prompt is built, from the target's harness or setting, as #896 decides today; rollout is test-team dummy chats on a test channel first, then the downstream team's lead coordinator switches to markers.

# Notes

[watermelon-full-preview] Implementation: `CoordinatorTranscript` follows a headless target's event log (`assistant.text` -> complete CHAT_REPLY blocks, byte-exact; synthesized Prompt/Text/ToolCall/TurnEnd events feed the existing trace `Collector` and turn marks). `reply_mode()` is decided per prompt from the followed source (headless log followed = marker prompt; no log yet = command-only), at startup and on `serving()` repoint, with no bridge restart; `chat reply --file` stays as fallback and dedups with log blocks through the shared capture store in both arrival orders. The headless owner loop captures from the log and runs the reply-source watch; receipts still require the model to start the prompt (#896 unchanged). One additive persisted field: `headless_log` (bool, serde-default, skip-if-false) on `ReplySource`, written in the bridge state dir's `reply-source.json` — not an agent registry record; older readers ignore/default it.

[watermelon-full-preview] Review fixes: (1) follower identity (record token + agent/events dir dev/ino, plus generation regression) resets a replaced log under the same name, clearing prior blocks; (2) the Muse headless adapter logs every completed agentMessage phase as assistant text (not only finalAnswer), tested; (3) `chat help` follows the request's recorded `reply_mode` (`BridgeState::recorded_reply_mode`), harness kind only as fallback; (4) the capture tick polls the reader cheaply, skips the full state scan/state lock when nothing changed, rescans when the delivered-and-unanswered set changes or at each reconciliation, and treats a capture error as logged-and-retried, never fatal; (5) first open is bounded via `events::read_recent(FIRST_READ_BYTES)` with the follower at end (trace first open still at end only).

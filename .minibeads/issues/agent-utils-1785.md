# Description

A consumer `wrkslots remove <slot> --archive-ignored --archive-private-history --no-lock-budget` returned 0 ("removed and archived") on build 6e80ecfb yet deleted the only copy of some private-history commits. It printed keep/drop lines for four checkouts but nothing for one nested submodule checkout, whose private store is now gone. That checkout's salvage ref inventory lists 1,310 refs/rescue/* refs pointing at 723 distinct commits; 721 exist in the parent module store, and 2 tips (two reflog-* rescue refs) are in no store the consumer can find. An addendum widens it: the same remove also dropped 20 refs/rescue/*/dangling-* and reflog-* tips of another checkout, whose receipt shows only "dangling, slot-only, past prune expiry: 23" with no SHAs; in total 22 rescue tips from that one remove are gone.

Root cause (proven in fixtures): the private-history scan in `py/wrkslots/cli.py` (`_submodule_private_history_uncached`, `_commit_tips`) collapses every positive root (refs, reflog endpoints, pseudorefs, every commit object) to maximal tips, then classifies each maximal tip by age (`_prune_expire_cutoff`, object mtime). A commit named by refs/rescue/* or refs/salvage/* is protected only when it is itself the maximal tip; a rescue-named commit that is an ancestor of an unnamed old maximal tip is lost with that tip when the tip is classified "dangling, slot-only, past prune expiry" and dropped. Dropped maximal tips are recorded only as receipt counts: `_PrivateHistory.not_kept` carries (category, commit, ref), but receipt builders write only `private_history_counts`, and the stdout not-kept line shows at most three tips truncated to 12 characters while claiming the rest are "counted in the salvage receipt". A checkout whose scan finds no kept tips (or no tips) gets no keep/drop line at all, because the keeping line is printed only by `_partition_kept_commits` on the keep-private-state salvage path. A ref tip whose object is missing makes the peeled `for-each-ref` format crash Git with a message naming neither the ref nor the tip, and several enumerations skip unscannable state silently (`_nested_module_repository_checkouts`, the pregather swallow, malformed reflog/ref lines). The scan's walks also do not set `GIT_NO_LAZY_FETCH`, so a missing object can be hidden by lazy fetch in a promisor repository. The Rust edition (`rs/wrkslotsd/src/remove_write.rs`) has no age drop but counts only heads/tags as named refs (rescue/salvage refs fall into the unreferenced count), gates only direct (non-recursive) submodules, silently skips submodules whose HEAD cannot be read, and hardcodes zero private-history counts with no dropped list in its receipt.

On whether the 2 missing commits could have been in the private store at all: a rescue ref created through Git in that store must have pointed at an object present at creation, because `git update-ref` refuses a nonexistent object. A reflog name is different: a reflog file is plain text and can name a commit a fetch only advertised (for example under a partial-clone filter), which the store never held as a complete object. The scan parses reflogs without an object check, so it cannot distinguish those cases after the fact.

# Design

Keep the change in the private-history/rescue-ref scan, its callers in remove (including the finish-removal tail, which shares the same scan), and the Rust mirror scan.

In the Python scan: enumerate refs without the peeled format that crashes on a missing object (peel through a batch check with lazy fetch off); judge every ref tip, reflog endpoint and pseudoref tip for local resolvability with `GIT_NO_LAZY_FETCH=1` on every scan walk. An unresolvable tip refuses removal by default, naming every unresolvable ref and SHA; with `--archive-unresolvable-private-history` removal bundles what it can and names every unresolvable tip in the receipt and on stdout. A commit named by any refs/rescue/* or refs/salvage/* ref is never dropped by the age/prune-expiry rule, even when it is an ancestor of a maximal tip rather than the tip itself, unless the separately named `--discard-rescue-ref-history` is given. Every dropped commit, for any reason, is listed by full SHA plus the ref that named it in the salvage receipt: inline up to 64 entries, beyond that a bounded summary plus a manifest sidecar file in the salvage archive in the style of #1772 (count, canonical digest, manifest path and digest). Every checkout scanned prints a keep or drop line, including "nothing private"; a checkout skipped for any reason prints why. The same rescue/dropped/unresolvable rules apply on the finish-removal path, and the Rust scan mirrors them (rescue/salvage refs named, nested submodules gated, unresolvable tips refused and named, dropped commits listed in its receipt).

# Acceptance Criteria

A nested submodule with a rescue ref whose object exists only in its private store is kept (bundled) or refused, never silently deleted, and prints a keep line; a nested submodule with a rescue ref whose object is missing refuses by default naming the ref and SHA, and with `--archive-unresolvable-private-history` bundles what it can while naming the unresolvable tip in the receipt and on stdout. A rescue- or salvage-named commit is never age-dropped, including when it is an ancestor of a dropped maximal tip, unless `--discard-rescue-ref-history` is given. Every checkout scanned prints a keep/drop line, including one with nothing private, and a skipped checkout prints why. Every dropped commit appears by full SHA and naming ref in the salvage receipt, inline or via the manifest sidecar when the list is long. Deterministic regression tests in both editions fail before and pass after.

# Notes

Deferred and follow-up (from the independent data-safety review, not fixed in this change): M3 — the shared-submodule scan branch enumerates every ref of the shared store for naming, so another slot's broken ref in that store can over-refuse this slot's removal and be listed as dropped here; judging shared-store unresolvable entries by this worktree's own reflogs/refs is a follow-up. Policy journaling route (a) — recording the private-history policy inside the finish journal's `x` extension without a version bump — is a follow-up for when readers can be bumped; this change journals nothing and re-supplies the policy on `recover` (route (b)), refusing a mismatched resume with a message naming both flags. Remaining LOW items: the salvage scan line's kept count can include commits the bundle partition later excludes as incomplete (the receipt's dropped list is authoritative); the pregather/prefetch `except Exception: continue` swallows remain, safe only because the locked path re-derives everything; the Rust editions' other stdin-fed Git commands share the batch writer pattern fixed in `peel_to_commits_batch`; a loose ref in a worktree's own Git directory that shadows a shared-store ref of the same name is judged only for object presence (Git's listed value stands for naming); and H3's fenced skip falls back to the candidate name alone when the candidate worktree cannot answer (its reported Git directory is compared whenever it can).

Two addenda while the scan was rewritten: (1) a thin salvage bundle could record prerequisites that exist only as refs inside the slot's own store, so `git bundle verify` passed there and failed in every surviving store once the slot was deleted — thin prerequisites must now be proven, in one batch, in a store that survives removal (otherwise the bundle is thinned only against surviving tips, i.e. fuller or complete), and every salvage bundle in the remove/finish paths is additionally verified against surviving stores only, refusing before anything is deleted when that fails; (2) a large remove in this scan's last phase ran roughly one Git process per tip (about 720 rescue tips) — ref enumeration, peeling, ancestry and remote lookups in the rewritten scan are batched (one `for-each-ref`, `cat-file --batch-check` peels, one parent walk), with a subprocess-count regression test on 60 rescue refs.

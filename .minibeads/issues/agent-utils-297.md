# Description

[opus 5.5] #208 persistent-cache, milestone M5 cache-fill. The blocking findings still open after the last M5 review round (three review lenses at be7ba6bc, before the rebase onto #287 bulk-reads; the code they touch did not change in the rebase), with the probes that show each one. **M9 cache-serve must not answer any read from the message cache until this issue is closed.** Until then the cache only fills and measures (the shadow counters), and the README's operator section says to leave it off. 1. **R6-A, false completeness: erase_scope against a racing listing.** MessageCache::erase_scope bumps the channel epoch when it is called, but the writer applies Op::EraseScope later. A Main read whose stamp is taken after the bump, and whose observed_ms is no later than the writer's apply time (a backlogged queue, or the same millisecond), lands after the erase. merge::revives needs observed_ms > deleted_ms, so the tombstone holds the reply (a Slack reply also sent to the channel) back, yet Writer::listing still stamps Main's claim over its instant. Below the band that undoes coverage::puncture; being the latest read, it also writes checked_from_ms back down, which in the band undoes give_up_instant. A window of 4 three seconds later and the Main timeline fallback an hour later decide Serve without a message upstream still lists. On a bridge the same follows with no race, because Fill::observed takes min(as_of, start). A thread listing stamped in the same window can rebuild the erased thread's head and coverage over its tombstoned replies, since confirmed() unblocks the thread scope straight after the erase. Probes: `r6_a_a_main_read_begun_before_a_thread_erase_was_applied_never_reclaims_the_reply` (three variants) and `r6_b_a_page_across_the_reclaimed_instant_is_never_served` in /tmp/r6fc/head/vibe-talk/src/cache/r6_probes.rs, log /tmp/r6fc/r6a-head.log; `rv1_a_main_read_begun_while_the_erase_was_queued_never_reclaims_r1s_instant` and `rv1b_strictly_between_the_erase_call_and_its_apply` in /tmp/rvcc/probe-be7ba6bc/vibe-talk/src/cache/rv_probes.rs. Suggested fix, a weakening: in Writer::listing, take out of the claim (coverage::puncture) every instant whose listed row a tombstone newer than the listing's start held back, and raise checked_from_ms past it in the band; or give an erase's tombstones a time that no read stamped after the bump can fail to beat. Add the pause_writer test. 2. **R6-C, a deleted or edited message comes back: the channel epoch bump discards pushed deletions as Stale and records no drop.** erase_scope bumps the whole channel's epoch while keeping its other scopes, so observe_op answers Outcome::Stale for every queued observation of the channel stamped before the bump, pushed deletions and edits of messages the erase keeps included. Only ops_stale is counted: no mark_suspect, no lost(), last_drop_ms stays None, and removes_only() observations are not applied. fed_since then vouches for the old row, message_by_id decides Serve on a deleted message or on text edited away, and the store's summary of the old text is never orphaned. A read-scope request can set it off: a bogus thread id answered `thread_not_found` (or a Discord-protocol 404), confirmed by the server's own read ten minutes later, runs erase_scope; on a bridge, a deleted thread's 404 is confirmed while the adapter is pushing that thread's deletions. Probes: `r6_c_a_thread_erase_never_discards_a_queued_deletion_of_another_scopes_message` in /tmp/r6fc/head/vibe-talk/src/cache/r6_probes.rs, log /tmp/r6fc/r6c-head.log; `r6_a_bogus_thread_erase_never_lets_the_feed_vouch_for_a_deleted_message` and `r6_a_bogus_thread_erase_never_lets_the_feed_vouch_for_an_edited_messages_old_text` (control: `r6_control_a_pushed_deletion_lands`) in /tmp/r6priv/head/vibe-talk/src/cache/r6_probes.rs, logs /tmp/r6priv/r6-head.log and /tmp/r6priv/r6-prev.log. Suggested fix: on a Stale op for a channel whose rows survive the erase, apply its removes_only() observations and record a drop for everything else; or give scope erases an epoch of their own, once R6-A's weakening is in. 3. **AccessWatch block/unblock race**, named by two lenses as to be fixed before anything is served. report() and confirm() call listener.block and listener.unblock after the doubts lock is released, so a refusal that raises a new doubt while a success clears the old one can leave the channel in doubt but unblocked for up to CONFIRM_AFTER (10 minutes). Probe: `cache::access::r5_probe::r5_a_new_doubt_raised_while_an_old_one_clears_stays_blocked` in /tmp/r5cf/probe-head/vibe-talk/src/cache/access.rs. Fix: block and unblock while holding the doubts lock, or re-check stands() before unblocking. 4. **R5-A, a false miss that skews the numbers M9 is to be judged by.** fresh() judges a head by head_listed_ms, which advance_head pins to the read that opened the band for as long as it is open, so in a quiet channel a window, a count or an open page asked two seconds after a read of the newest end is Miss(StaleHead), for up to ten minutes after each new message. It never claims completeness, but it under-counts the shadow hit rate where the cache would help most. Probe: `r5_a_a_window_two_seconds_after_a_read_of_the_newest_end_is_not_stale` in /tmp/r5fc/probe/vibe-talk/src/cache/r5_probes.rs. Fix: measure freshness against checked_ms. Also open, non-blocking, to settle before M9: a control erase that fails (disk full, busy) is never retried and its block lives in memory only; erase_channels, erase_scope and erase_provider re-insert their pending entry with HashMap::insert, so an earlier erase can lower a later one's sequence, or re-insert u64::MAX after erase_file cleared the map; LiveHub::publish_read takes a fresh stamp at publish time rather than the tick's; a Discord-protocol provider's 403 or 404 counts as lost access whatever its body (an HTML 404 from a proxy would erase every channel); an AccessWatch provider key never given a dialect defaults to the more erasing DiscordProtocol; two reads of the newest end begun in the same millisecond can leave a deleted band row vouched for; give_up_instant rewrites a scope's coverage once per erased row; and since #307 slack-reply-live a Slack window upstream carries the thread replies Flat holds for the threads active among the newest messages, which the cache holds in their threads alone (a window holding one is rows only), so where the cache would have served a Slack window for the messages family, the replies upstream listed count as missing rows: M9 must answer a Slack window from Main and those threads' scopes, or not at all. Found by the two landing reviews of the rebased branch at 52879ddb (both approved; one checked that the cache off changes nothing, the other the rebase's fidelity): **to settle before M9, a Slack reply from Flat's memory is offered as newer than it is.** A Slack reply whose text comes from Flat's memory can be up to FLAT_RECONCILE (15 minutes, slack/timeline.rs) stale after an edit, yet the cache is offered it as read at the window's start, so merge::content_verdict, which replaces held text whenever the observation is later, can put old text back over newer text: a lookup by id brings the edited text into the cache, and a /messages window a minute later restores the old text. The Slack Flat timeline page does the same, so this was in M5 before the rebase; #307 slack-reply-live widened it to /messages, the voice tools, the catch-up, find_message and reads of several channels. With the cache on, the store's summary of the current text is deleted (a re-summarize); under M9, stale text would be served. Possible fixes: date a Flat-memory reply from that memory's full read, or have a Slack lookup check Flat's memory as the thread view does. Probes: `review_probe_a_slack_window_from_flat_memory_never_reverts_an_edit_a_lookup_learned` and `review_probe_flat_page_variant`, appended to ~/agent_scratch/m5-review-1/mut/vibe-talk/tests/message_cache_fill.rs, logs ~/agent_scratch/m5-review-1/probe1.log and probe2.log. **Acceptable for M9: two ways a server with no [message_cache] table differs from one built before the cache existed.** The equivalence review found every upstream and summarizer call identical at about 1,450 steps over five fakes, with the table absent and with enabled = false (harness ~/agent_scratch/m5-review-0/harness/zz_eq.rs, reports ~/agent_scratch/m5-review-0/eq-absent.txt and eq-disabled.txt, process level ~/agent_scratch/m5-review-0/proc/results.json), and named these two. First, main.rs spawns cache::sink::log_every_hour whatever the configuration: one task that wakes each hour, gets None from Sink::report() and returns, with no I/O and no log line. It reads and serves nothing, so it does not bear on M9; spawning it only when `state.message_cache.lifecycle().is_some_and(|l| l.configured())` is a tidy-up. Second, lifecycle::start always attaches a Lifecycle, so purge_storage (http/api.rs) runs Lifecycle::purge on a cache-less server too: it reads the sidecar, scans the store's directory, erases nothing, and logs "the store was erased, and every message cache file this server made with it" bytes=0, a line main never writes (in results.json it is in all four M5 runs and in none of main's), which the README's "behaves as it did before the cache existed" does not allow for. The call itself must stay, because an absent table leaves a cache file from an earlier configuration in place for seven days and the purge is what erases it then; the fix is to log the line only when bytes > 0, not to skip the call when the table is absent. Neither difference touches what M9 serves or what is read upstream, so neither has to change before M9; fix the second, or qualify the README's sentence, the next time that code is touched. Two more from rebasing the branch onto #319 slack-reply-by-id and #320 slack-edited-mark. **To settle before M9:** a lookup by id that finds a reply only in the thread the server already knows it to be in (ops::message_by_id's known_thread fallback, #319) is shadowed by its first read alone. Where the provider's lookup proved the id absent from the channel (Slack's history holds no reply) and the cache would serve the reply, the shadow compares that copy with an upstream answer that listed nothing and counts it as extra, although the server then answers with the reply. The fallback read is not shadowed again, so nothing is counted twice, but the message-by-id figures overstate the cache's differences for Slack replies. And for the Flat-memory finding above, a third possible fix: #320 gives a Slack message its edit time (Message::edited_timestamp), yet Incoming::new leaves edited_ms None, so merge::content_verdict never sees one; carrying it, and letting no copy whose edit is older than the held copy's replace it, would keep the newer text. [opus 5.5] Delivered on branch vt/297-cache-coverage-races in "vibe-talk: close the message cache's coverage races before it serves". Blocking items: (1) R6-A: a listing never claims an instant whose row it carried but a tombstone made after its read began held back (that tombstone may be the cache's own scope erase), and the latest read of the newest end records its listing as whole only above such a row, so neither Main nor the erased thread is re-claimed without the reply (pause_writer test included). (2) R6-C: a scope erase moves an epoch of its own; an observation begun before it has its deletions applied and anything else recorded as left out (a drop), never discarded silently. (3) AccessWatch: block and unblock (and a confirmation's end) run under the doubts lock; a listener installed later blocks what is in doubt the same way. (4) R5-A: freshness is judged by the latest read of the newest end (checked_ms). Must-settle items: the Flat-memory reply (a message's edit time now reaches merge::content_verdict; a copy whose edit is older than the held copy's, or one reporting no edit from a provider whose every copy reports edits, never replaces it nor the rest of the message), and the #319 known-thread fallback (the lookup's shadow evaluation waits, noted, for the fallback's answer and is compared with it). Settled from the non-blocking list: a refused erase is retried after a backoff until carried out; erase_* record their pending entry under the lock reads check (no lowered sequence, no u64::MAX left across a file erase); give_up_instant rewrites a scope once per erase; publish_read is offered under the tick's stamp; a Discord-protocol 403/404 counts only with the provider's own JSON error body; an unset dialect is Unknown (401 only); the hourly sink task starts only with a table; the purge logs only when bytes > 0. Each probe is a test that fails at 4e229c01 and passes on the branch. Remaining, non-blocking: (a) the block of a refused erase is in memory only: the file that refused cannot record it, and a durable record needs the sidecar beside the store (a format and startup change), so a restart while the file still refuses forgets the erase until the refusal is heard again (the README says so); (b) two reads of the newest end begun in the same millisecond can still leave a deleted band row vouched for (a tie rule: on equal checked_ms vouch only what both listed); (c) M9 must answer a Slack window from Main and the scopes of the threads its replies come from, or not at all: a requirement on cache-serve's design, not on the fill; (d) the pending-entry ordering fix has no deterministic test: the interleaving it closed is now inside one call under one lock.

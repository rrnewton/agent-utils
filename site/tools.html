Tools

The tools

Each tool starts with the problem it solves, then what you get and what it needs. Each agent-utils tool documents itself: run it with quickstart or --help.

Five tools exist twice, as independent Python and Rust editions that share their core commands and output. A harness runs the Rust edition unless you ask for Python. The badge on each tool says which it has.

Core

agentctl and wrkslots are always set up; the chat bridge can be connected later. Together they give one coordinator named sessions, isolated workspaces, and a way for you to reach it.

agentctl

corebetaPython + Rust

Start, message, read and stop coding agents by name, while each agent's terminal stays open to you.

Problem
You run several long-lived agents. Each follow-up must reach the right one exactly once, the team must survive crashes and reboots, and you still want to type into any agent directly.
What you get
Named sessions in a local registry. A durable prompt queue that never resends a prompt it cannot confirm: exit 75 means safely pending, 76 means possibly submitted. Launch profiles you write, with model and effort per profile. Attach and take over at any time, and restore a whole team after a reboot.
Agent CLIs
Claude Code and Codex, plus any other terminal agent through harness-neutral screen rules. Claude Code also runs headless, under the same names and commands. The support matrix says what works for each.
Needs
Linux, a Rust toolchain (or Python 3.10 or newer), and Herdr; agent panes can also run in tmux. No hosted account and no always-running manager.
Status
Core and beta, at version 0.1. agentctl wait reports that an agent is ready for input, not that its work is done.
Editions
Python and Rust share the interactive core and one user guide. Rust, the default, adds the chat plugin host, the coordinator inbox and restore; Python keeps the Google Chat polling bridge.

Key capabilities

  • start, send, read, wait, status, list and stop on named sessions.
  • Checks the recipient pane before and after typing, reads it back to confirm delivery, and quarantines a likely misroute.
  • Launch profiles in a private .agentctl/profiles.json: agent CLI, model, effort, arguments and environment, passed without shell expansion.
  • start --slot runs an agent inside a wrkslots slot.
  • restore brings back every agent that was running at shutdown, then the chat bridge and other services.
  • doctor compares the registry with Herdr; capabilities lists what this installation includes.

wrkslots

corePython

Gives each agent its own Git worktree slot and branch, records who owns it, and removes it only when nothing uses it.

Problem
Agents on one machine need checkouts that do not collide, do not fill the disk, and do not lose work when an agent dies.
What you get
Agent slots, salvaged before removal, and disposable validation slots. Handoffs, holds, and reports of unpushed work. A hash-linked event history that recovers after a crash.
Needs
Python 3.10 or newer, Git and Linux. Disk-image slots need passwordless sudo or fuse2fs. Running a command in a slot's box needs a systemd user manager, plus user namespaces or sudo.
Status
Core, at version 0.10. The box is an accident boundary for cooperative agents, not a security boundary.
Editions
Python. A Rust edition is being ported command by command; WRKSLOTS_ENGINE=rust opts in.

Key capabilities

  • create provisions and registers a slot on a fresh branch in one step.
  • Removal needs an expired time-to-live, a dead owner, and agreement from process, mount, Git and path checks. Missing evidence means refusal.
  • Unpushed commits go to a salvage remote or a verified local bundle before anything is deleted.
  • Storage: a plain directory, one sparse ext4 image per slot (about 70 MiB when fresh), or one shared btrfs image for every slot.
  • wrkslots run SLOT -- CMD: per-slot systemd limits, a private /tmp, and only the slot and named paths writable.
  • status, doctor, audit, unpushed, hold, clean-caches and recover.

agentctl chat

coreconnect laterPython + Rust, different bridges

Connects a Slack or Google Chat channel to one coordinator: allowed messages are typed into its pane, and its replies go back to the thread.

Problem
You want to hand the coordinator work, and hear back, while you are away from the terminal.
What you get
Messages from allowlisted senders only, stored before anything else happens. A reaction that means "received". Each reply posted to the right thread exactly once. A delivery whose outcome is unclear is recorded, never retyped.
Needs
Herdr. For Slack: the Slack provider (built with cargo), a Slack command-line client on the host, a Slack app to post replies, the channel ID and your user ID. For Google Chat: a space ID, your user ID and an OAuth token.
Status
Core; connect it at setup or later. Slack is event-driven. Google Chat is polled, hourly by default; --interval shortens that. Prompts arrive as pasted terminal input, and a reply cut off by Herdr's scrollback fails visibly instead of being guessed.
Editions
Two bridges. Rust: an event-driven host for provider plugins, used for Slack. Python: the Google Chat polling bridge.

Key capabilities

  • One bridge connects one channel to one coordinator.
  • Several replies per request: progress updates, or one reply per topic.
  • Restart-safe: requests and replies live in the bridge's state directory.
  • Slack messages with files arrive with each file's ID and download command.
  • A gap in the provider's event stream stops the bridge rather than risk a lost message.

Herdr

externaltested with 0.8

A separately maintained, persistent terminal server. Every agent in a harness runs in one of its tabs.

Problem
Agents need a terminal that outlives whatever started them, and you need to attach to any agent's real interface and take over.
What you get
Workspaces, tabs and panes with a command-line and socket interface. agentctl, herdr-run and the chat bridges drive it.
Needs
Install it from upstream and start it once with herdr. Setup offers to install it.
Status
External, last tested with Herdr 0.8. agentctl can also drive agent panes in tmux.

herdr-run

optionalPython + Rust

Runs an allowlisted command in a visible Herdr pane, outside whatever confines the caller, and returns its real output and exit code.

Problem
A sandboxed agent needs a sanctioned, visible way to run a blocked command such as git push, gh or a dependency fetch.
What you get
A per-project allowlist, .herdr-run.yaml, that only a person widens. Exact output and exit status, distinct codes for refusals, and an audit log, in a pane anyone can watch.
Needs
Linux, a systemd user manager, and Herdr.
Status
Optional, at version 0.4. The allowlist is a safety rail for cooperative agents, not a security boundary. A command that outruns its timeout keeps running.
Editions
Python and Rust, cross-checked by differential tests.

Key capabilities

  • Checks the bare program name against policy, re-quotes every argument, and refuses known escapes.
  • Captures results through files, not by scraping the screen.
  • Never types over a person: one lock per pane, and conservative readiness checks.
  • A cap on tabs; net-doctor checks that a pane can reach what the sandbox cannot.

tick-hub

optionalPython + Rust

One timer evaluates many recurring duties, each on its own cadence, and prints stable lines such as ACTION: and HEALTH:.

Problem
A coordinator has many recurring duties: reports, freshness checks, conditions a shell command can test. Without tick-hub, each needs its own timer and its own format.
What you get
Reminders with cadences, flags, shell gates and dependencies. File-freshness checks that report ok, stale or missing. A deterministic line protocol; state is written only with --flush.
Needs
A Rust toolchain or Python 3.10 or newer. In a harness, a systemd user timer.
Status
Optional, at version 0.2. In a harness, a 15-minute timer sends any tick with an ACTION: line to the coordinator with agentctl send. Action handlers must be idempotent.
Editions
Python and Rust, cross-checked by differential tests.

dagrun

optionalPython + Rust

Runs a dependency graph of build and test steps with bounded concurrency, cgroup containment and per-step profiling.

Problem
Run one step at a time, validation is slow. Run all at once, it overloads a shared machine, and one runaway step can take the host with it.
What you get
Steps in dependency order under limits on active steps, CPUs, memory and named resources such as a browser. Every step boxed in a cgroup. Profiles, speedup sweeps, and timeouts that capture evidence before they kill.
Needs
A Rust toolchain or Python 3.10 or newer, cgroup v2 and a systemd user scope. Without containment, a run refuses unless you pass --allow-cgroup-failure.
Status
Optional, at version 0.15. This repository runs all of its validation through it.
Editions
Python and Rust, cross-checked by differential tests.

Key capabilities

  • Strict JSON or YAML graphs with include fragments; list, ASCII, dot, JSON and YAML views.
  • Planners: longest-first, critical path, and CPA, which sizes each step from measured speedup curves.
  • Profiles, speedup sweeps and an HTML profile report.
  • dagrun capabilities reports which limits this host can enforce.
  • Ships cpuset-alloc for hard CPU reservations.

cpuset-alloc

optionalships with dagrunPython + Rust

Reserves disjoint CPU sets in a ledger shared across processes, and hard-pins a benchmark's whole process tree.

Problem
Concurrent benchmarks on one host need CPU cores that do not overlap, and reservations left by crashed processes must be reclaimed safely.
What you get
cpuset-alloc run --cores N --tag T -- CMD runs the command in a cgroup verified to hold only its reserved CPUs, plus status and reclaim.
Needs
Linux cgroups. It ships inside dagrun.
Status
It refuses to run when hard pinning cannot be proved, and never falls back to an affinity mask a process could escape.

parallel-experiment-runner

optionalPython

Runs concurrent seed-sweep workers under dagrun's containment, each with enforced CPU, memory, process-count and wall-clock limits.

Problem
Fuzz sweeps, flaky-test hunts and parameter scans can pile up processes and saturate a host.
What you get
Each seed becomes one boxed dagrun step. Concurrency is sized from measured idle cores after a short calibration. A cost estimate comes first and measured actuals after. A breach kills the worker's whole process tree and names what it breached.
Needs
Python 3.10 or newer, dagrun and cgroup v2.
Status
Optional, at version 0.3. A resource box against bugs, not a security sandbox.
Editions
Python only.

agent-teams

optionalbuild from sourceRust

Sends a message from one team's coordinator to another's, on the same host or another, exactly once.

Problem
Teams of agents run on several machines. Reaching another team's coordinator means knowing which host it is on and how to type into it, and a retry after an unclear outcome delivers the message twice.
What you get
One command to message another team. Each message carries one ID, and the receiving host claims it in a ledger before delivering, so a retry or a second route never delivers it twice. Routes run locally, over SSH, through a command, or through a shared chat channel. Nothing drives a remote terminal: the receiving host does its own typing.
Needs
One Rust binary per host. Herdr and agentctl are optional; with agentctl, messages land in the coordinator's prompt queue.
Status
Optional, at version 0.1, built from source. Only a team's coordinator or a registered service may send, and only to another team's coordinator.
Editions
Rust only.

merge-queue

experimentalbuild from sourceRust

A local merge queue that orders, batches, validates and lands ready changes while keeping the base branch green.

Problem
Landing ready changes one at a time costs one rebase and one validation each. Landing them all at once breaks the branch when two conflict, or pass alone but fail together.
What you get
Changes grouped by Git's exact conflict graph, ordered by priority and age, and split into batches. Each batch's combined tree is validated, several at once, and lands only when green. When a batch fails, only the failed tests rerun to find the culprit, which is ejected with a report while the rest lands. A change it cannot land gets a reason and the action that unblocks it.
Needs
Git 2.40 or newer and a Rust toolchain. It runs against a local clone: no service, no webhook.
Status
Experimental, at version 0.1, built from source. run --dry-run and run --shadow show what it would land before it lands anything.
Editions
Rust only.

wrkviz

optionalPython

Builds a zoomable local website from agent transcripts: a timeline of what a coordinator and its subagents did.

Problem
After days of multi-agent work, it is hard to see who did what and when, and what each phase achieved.
What you get
One track per agent, with fork and join edges and active, waiting and idle time. Cached summaries from a phrase up to a quarter. A static site served on 127.0.0.1, and a command-line query tool. It reads Claude Code and Codex transcripts, including nested subagents.
Needs
Python 3.10 or newer. Summaries use an installed Codex or Claude Code CLI, or an offline heuristic.
Status
Optional, at version 0.1. Only the summary stage makes model calls. Archives contain transcript text; treat them like logs.
Editions
Python. A Rust edition is being ported command by command; WRKVIZ_ENGINE=rust opts in.

gh-paced

optionalbuild from sourceRust

A wrapper in front of the GitHub CLI that charges every gh call against budgets and waits, or refuses, before GitHub pushes back.

Problem
Agents looping over gh, on several hosts that share one account, can trip GitHub's secondary rate limits, and an account that keeps calling risks suspension.
What you get
Each call classified as read, search, write or credential, and charged against per-host budgets sized to keep four hosts on one account well under GitHub's limits. One write in flight at a time, a 15-minute pause after any rate-limit response, and a guard against oversized write bodies.
Needs
Linux, the real gh binary, and a Rust toolchain.
Status
Optional, at version 0.1. Hosts do not share state, and only calls made through it are paced.
Editions
Rust only.

agent-usage

optionalbuild from sourceRust

Reports plan usage, reset times and burn rates for Claude Code and Codex, plus local token use, without a model call.

Problem
Agents cannot see their own budgets. A person can type /status; an agent would need a throwaway session or a paid model call.
What you get
Each plan window with percentage used and reset time. Burn over 15 minutes to 24 hours, and whether a window would fill before it resets. Local token use from transcripts. Text, JSON or one-line output, and optional 15-minute history.
Needs
Linux or macOS, curl, and a Rust toolchain.
Status
Optional, at version 0.1. Plan percentages exist only for subscription logins; API-key setups get local burn only.
Editions
Rust only.

minibeads

optionalsubmoduleRust

A small, dependency-aware issue tracker, mb, that keeps each issue as a Markdown file in the repository's .minibeads/ directory, committed with the work.

Problem
A coordinator hands out many small tasks a day. On GitHub they crowd out real bug reports and spend a shared rate limit; in chat, nobody can see what is in flight or what was never closed.
What you get
Issues with priorities, labels, comments and dependencies. mb ready lists unblocked work. An atomic claim marks a task in progress for one agent. JSON output for scripts, and a sync to GitHub Issues for the few tasks that belong there.
Needs
A Rust toolchain: git submodule update --init ext/minibeads, then cargo install --path ext/minibeads --bin mb, or cargo install minibeads from crates.io. No database and no service.
Status
Optional, developed in its own repository and pinned here as a submodule. agent-utils uses it for its own tasks, but no tool depends on it; any tracker works.
Editions
Rust only.

vibe-talk

optionalearlyRust service

A small Rust server and web app for reading and answering your agents' chat on a phone or desktop. Its own page shows it in five short clips.

Problem
Agents post long messages, many of them before you look. Ordinary chat clients are built for people, not for a stream of agent reports.
What you get
One-line summaries of long messages, named threads, and Discuss, a side agent that catches you up on a channel. Done, read modes, pins and search for triage. A Documents view of everything linked in chat. Replies, read-aloud and voice conversation. Separate read and write tokens, and posts that cannot ping @everyone.
Needs
A host to run it, natively or in a container; TLS in front if you expose it; a chat credential (Slack, Discord, or a Google Chat bridge); and optionally a model provider for summaries and a voice vendor.
Status
Optional and early, at version 0.1. Its live Discord and voice-vendor paths are not yet verified.
Editions
One Rust service with its own Cargo workspace and CI. No agent skill.

pr-landing-planner

experimentalPython + Rust

An advisory planner that turns a queue of pull requests into per-PR actions and conflict-safe groups.

Problem
Landing many pull requests means working out which conflict, what order they need, whose CI still applies to the exact head, and which can land together.
What you get
Real merge-conflict detection, dependency ordering, CI classification, and evidence tied to each PR's exact head. Output for people, as JSON, or as line-oriented actions. An offline fixture mode, and a live mode that uses gh and git.
Needs
A Rust toolchain or Python 3.10 or newer; gh and git for live mode.
Status
Experimental, at version 0.1. It never merges, rebases or labels a pull request; a separate operator does any landing.
Editions
Python and Rust, cross-checked by differential tests.

chat-subscription libraries

libraryRust

Rust libraries that let chat providers plug into the chat bridge as separate processes.

Problem
A chat bridge must not lose or double-process messages across disconnects, and providers should plug in as separate programs without credentials in the protocol.
What you get
Ordered events, replay cursors, explicit gap events and a durable acknowledgement boundary, carried over a versioned JSON process protocol. A fake provider for conformance tests.
Status
Version 0.1. The Slack provider is the first plugin; it is built from source, not published. Plugins are trusted code running as your user.

Installing a tool on its own

In a harness nothing needs installing: the commands in agent-utils/bin run from the checkout, and Cargo builds the Rust ones on first use. To use one tool on its own, install it from a checkout of this repository:

python3 -m pip install ./py/wrkslots      # a Python distribution
cargo install --path rs/agentctl          # a Rust crate

No agent-utils package is published to a package index yet. The Python distributions and Rust crates list them all.

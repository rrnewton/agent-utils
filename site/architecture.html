Architecture

How the suite fits together

One level below the overview figure: what each layer does, how one task moves through it, and where state lives.

Layers and responsibilities

Each layer has one job and a narrow interface to the next. The coordinator reaches subagents only through agentctl and wrkslots, and only the coordinator talks to you.

The owner

You decide what gets done and you own the policy. The coordinator writes launch profiles exactly as you state them, never invents models or flags, and changes the skills or the harness AGENTS.md only when you ask. Only you widen the herdr-run allowlist.

Skills and instructions are owner-controlled

The owner channel

The simplest channel is the coordinator's Herdr tab: attach and type. Run agentctl pause first if a script also types into that terminal.

agentctl chat connects one Slack or Google Chat channel to the coordinator. It accepts messages only from allowlisted senders, stores each one, and reacts to mark it received. Herdr pastes the message into the coordinator's pane, and the coordinator's reply goes back to the thread exactly once.

The Rust bridge is event-driven and takes providers as plugins; Slack is the first. The Python bridge polls Google Chat, hourly by default.

vibe-talk is a separate phone and desktop client for the same chat. It reads and posts messages but never controls agents, so with agentctl chat on the same Slack channel, you read and answer the coordinator from vibe-talk.

The coordinator

The coordinator is an ordinary coding agent started in the harness root. It reads the harness AGENTS.md and the coordinator skill at the start of every session. The harness file wins where the two disagree, and inside the checkout the project's own rules win.

Its priorities, in order: what you asked; a red main branch; work in flight; the backlog. Setup registers it as the agentctl session coordinator, so timers, scripts and other agents reach it with agentctl send coordinator. A coordinator on another machine leads another team, and agent-teams carries messages between the two.

Sessions: agentctl on Herdr

Herdr is a persistent terminal server, installed separately. Every agent runs in its own Herdr tab, so you can attach and take over at any time. agentctl can also drive agent panes in tmux.

agentctl keeps a registry of named sessions in the harness's private .agentctl/ directory, with no hosted account and no manager process. Prompts go through a durable queue. Exit code 75 means a prompt is safely pending; agentctl drain retries it. Exit code 76 means it may already have been submitted, so it is set aside and never resent automatically. agentctl start --slot starts an agent inside a slot, and agentctl restore brings the team back after a reboot.

Workspaces: wrkslots

Each task gets a slot: a linked worktree of the primary checkout, on a fresh branch from the remote default branch. Where the host allows it, each slot lives in its own sparse ext4 image, so a runaway build fills its own image rather than the disk. Every slot gets systemd resource limits. An optional sandbox makes only the slot and named paths writable; it guards against accidents, not attacks.

wrkslots records ownership in a hash-linked event history, and removes a slot in one of two ways. Reclaim needs an expired time-to-live, a dead agent (asked through bin/agent-liveness), and agreement from process, mount, Git and path checks. Release is quicker: the owner writes a handoff and gives the slot back, and the coordinator reads the handoff before removal. Either way, unpushed commits are saved to a salvage remote or a verified bundle first.

Recurring work: tick-hub

tick-hub decides which reminders and freshness checks are due and prints lines such as ACTION: and HEALTH:; it schedules and delivers nothing itself. In a harness, a systemd timer runs it every 15 minutes and sends any output with an ACTION: line to the coordinator with agentctl send, the same queue your messages use.

Validation and landing

Your project's rules decide how work lands: pull requests or direct pushes, required reviews and checks. The coordinator validates before it pushes and checks the result on the remote afterwards. dagrun runs validation locally under resource limits. merge-queue batches ready changes and lands only green combined trees. herdr-run pushes when the agent's sandbox blocks the network, gh-paced paces GitHub calls, and pr-landing-planner proposes a landing order without acting on it.

A delegated task, end to end

The path in the harness AGENTS.md template, with the sandbox off (the default). $WS is the harness's wrkslots command and $AU its agent-utils bin/.

  1. You ask owner

    In the coordinator's tab or in chat: "Please have a subagent add CONTRIBUTING.md and land it." The coordinator names the task with a short slug, such as add-contributing, and picks the repository, slot and branch.

  2. A fresh slot coordinator · wrkslots

    A slot starts from the remote-tracking branch, so the coordinator fetches first:

    git -C <primary> fetch origin
$WS create <slot> --slot-type agent --coordinator-authorized \
  --agent <name> --task <slug> --purpose "<one line>" \
  --coordinator-pid <pid> --repo <primary>=<primary> \
  --branch <primary>=<name>/<slug>

  3. A subagent with a brief coordinator · agentctl

    It starts a subagent in the slot with one of your launch profiles and a brief: the goal, the slot and branch, how to validate and how to report.

    AGENTCTL_WRKSLOTS_BIN=$WS $AU/agentctl start <name> --cwd <harness> \
  --profile <profile> --slot <slot> --file <brief>

    The subagent opens as a new tab in the project's Herdr workspace. Every task gets a fresh agent.

  4. Work in the slot only subagent

    The subagent takes ownership of the slot (wrkslots adopt), commits only on its branch, and publishes as the project requires. Then it writes a handoff (what changed, the commit, how it was tested, open questions), releases the slot and replies.

  5. Supervise coordinator

    agentctl status and agentctl read show progress, and the subagent's reply says when it is finished. If a delivery is uncertain (exit 76), the coordinator looks before it resends.

  6. Check the work coordinator

    It reads the diff, the test output and the pushed commit, then the handoff ($WS read-handoff), and checks which tests ran on which commit.

  7. Stop and remove coordinator · wrkslots

    $AU/agentctl stop <name>
$WS remove <slot> --coordinator-pid <pid> --expected-generation <n>

    wrkslots refuses unless nothing uses the slot, saves unpushed commits first, and names the reason for any refusal.

  8. Land coordinator

    It validates with the project's own command, lands as the project allows, and checks the result on the remote.

  9. Report coordinator → owner

    It tells you what changed and why, cites work as #<number> <slug>, and says what it did not check.

With the sandbox on

A sandboxed subagent cannot write the wrkslots registry, so it replies with its handoff instead, and the coordinator removes the slot after agentctl stop once its time-to-live has passed.

The harness directory

Setup turns the checkout you started in into the harness root and moves the checkout inside it, unchanged. For a repository foobar:

~/work/foobar/                  harness root; the coordinator runs here
├── AGENTS.md                   you are the coordinator; layout, tools, delegation,
│                               suite configuration, and your project rules
├── foobar/                     primary checkout, an independent repository
├── agent-utils/                clone, submodule, or symlink to an existing checkout
│   ├── bin/                    tool dispatchers; Rust edition by default, built through Cargo
│   └── skills/
├── worktrees/                  wrkslots control directory
│   ├── slots/<slot>/           one checkout (or disk image) per task
│   └── wrkslots                the wrkslots command for this harness
├── bin/agent-liveness          exit 0 dead, 1 alive, 2 unverifiable
├── .agents/skills/             links into agent-utils/skills/
├── .claude/skills -> ../.agents/skills
├── .agentctl/                  session registry and launch profiles; private
└── .wrkslots.yml               slot policy, commented key by key

The harness is its own small Git repository, local unless you add a remote, so its configuration is versioned. Its .gitignore excludes the checkout, agent-utils/, worktrees/, .agentctl/ and chat configuration, and agentctl refuses to use launch profiles unless .agentctl/ is ignored.

Skills are linked, not copied, so updating agent-utils updates them. The bin/ dispatchers run each paired tool's Rust edition, built by Cargo on first use; DAGRUN_ENGINE=python (or AGENT_UTILS_ENGINE=python) runs Python instead, and there is never a silent fallback. The Rust default needs cargo on PATH wherever the tools run, timer services included.

Everything the suite keeps is a file on your machine. There is no hosted service and no database server.

Decisions, findings and landing evidence go in the project's issue tracker, pull requests or tracked files, not in a terminal or a chat thread.

How you stay in the loop

One voice

Only the coordinator talks to you. Subagents report to it, and it sums up: what changed, why, and the numbers behind it.

References you can follow

Work is cited as #<number> <slug>, and anything an agent publishes, such as a commit body, says which agent wrote it.

Eyes on every agent

Each agent is a real terminal in a Herdr tab. Attach, read along, or pause automation and type.

Policy stays yours

Launch profiles, the herdr-run allowlist, the skills and AGENTS.md change only when you ask. "Turn on the sandbox for subagents" is a request to the coordinator.

Limits

  • Linux only. wrkslots, dagrun and the slot limits need systemd and cgroup v2. agent-usage also runs on macOS.
  • Not a security boundary. The slot sandbox and the herdr-run allowlist stop accidents by cooperative agents, not a hostile one.
  • Ready is not done. agentctl knows when an agent is waiting for input; only the agent's reply says the task is finished.
  • Herdr is a separate project, last tested at 0.8.
  • Two chat providers. Slack, through the event-driven bridge and a Slack command-line client, and Google Chat, polled.
  • Pre-1.0. agentctl is beta, and every version is below 1.0.

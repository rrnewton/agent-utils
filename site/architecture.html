The owner

You choose the work, agent models and launch settings. The coordinator follows your project rules; changes to those rules or the command allowlist need your approval.

Skills and instructions are owner-controlled

The owner channel

The simplest channel is the coordinator's Herdr tab: attach and type. Run agentctl pause first if a script also types into that terminal.

agentctl chat passes messages from allowed senders in a Slack or Google Chat channel to the coordinator. It stores requests before delivery and posts replies back to the thread.

The Rust bridge handles Slack events through a provider plugin. The Python bridge polls Google Chat, hourly by default.

Use vibe-talk to read and answer those messages from a phone or desktop on the same Slack channel.

Chat user guide · The Slack provider · How an agent answers bridged chat · Plugin protocol

The coordinator

The coordinator is an ordinary coding agent started in the project folder. Its AGENTS.md and coordinator skill describe how to delegate, check and land work. Your project's rules take precedence.

Its priorities are your requests, a failing main branch, work in progress, then the backlog. Reach it with agentctl send coordinator; use agent-teams to reach coordinators on other machines.

Sessions: agentctl on Herdr

Interactive agents run in Herdr tabs or tmux panes you can attach to. Headless workers use the same named agentctl commands.

agentctl stores named sessions and pending prompts in the private .agentctl/ directory. agentctl drain retries pending prompts; uncertain deliveries are set aside for inspection. Use start --slot to launch an agent in a worktree and restore to restart a saved team.

agentctl user guide · Observe and take over · Boxing an agent to a slot · Restore after a restart

Workspaces: wrkslots

Each task gets a worktree on a fresh branch. Choose directory storage, an ext4 image per slot or a shared btrfs image. Run agents with CPU and memory limits, plus optional restrictions on where they can write.

wrkslots records who owns each slot and preserves unpushed commits before removal. Cleanup waits until no process uses the slot. An owner can release a finished slot with a handoff; abandoned slots need expiry and liveness checks.

Recurring work: tick-hub

The setup template runs tick-hub every 15 minutes with a systemd timer. It checks which reminders are due and which files are stale. The timer script forwards any tick containing an ACTION: line to the coordinator through agentctl send.

Validation and landing

The coordinator runs your project's checks and follows its review and landing rules. Add dagrun for resource limits, merge-queue to test and land batches, or herdr-run for allowlisted network commands. gh-paced limits GitHub calls; pr-landing-planner suggests a landing order.

A delegated task, end to end

This example uses the default setup, with the sandbox off. $WS is the wrkslots command and $AU the agent-utils bin/ directory.

  1. You ask owner

    Ask in the coordinator's tab or in chat: "Have a subagent add CONTRIBUTING.md and land it." It picks a worktree and branch for the task.

  2. A fresh slot coordinator · wrkslots

    A slot starts from the remote-tracking branch, so the coordinator fetches first:

    git -C <primary> fetch origin
$WS create <slot> --slot-type agent --coordinator-authorized \
  --agent <name> --task <slug> --purpose "<one line>" \
  --coordinator-pid <pid> --repo <primary>=<primary> \
  --branch <primary>=<name>/<slug>

  3. A subagent with a brief coordinator · agentctl

    It starts a subagent with your launch profile and a brief covering the task, worktree, tests and expected result.

    AGENTCTL_WRKSLOTS_BIN=$WS $AU/agentctl start <name> --cwd <harness> \
  --profile <profile> --slot <slot> --file <brief>

    The subagent opens as a new tab in the project's Herdr workspace. Every task gets a fresh agent.

  4. Work in the slot only subagent

    The subagent takes ownership of the slot (wrkslots adopt), commits only on its branch, and publishes as the project requires. Then it writes a handoff (what changed, the commit, how it was tested, open questions), releases the slot and replies.

  5. Supervise coordinator

    agentctl status and agentctl read show progress, and the subagent's reply says when it is finished. If a delivery is uncertain (exit 76), the coordinator looks before it resends.

  6. Check the work coordinator

    It reviews the diff, test output and handoff against the pushed commit.

  7. Stop and remove coordinator · wrkslots

    $AU/agentctl stop <name>
$WS remove <slot> --coordinator-pid <pid> --expected-generation <n>

    wrkslots refuses unless nothing uses the slot, saves unpushed commits first, and names the reason for any refusal.

  8. Land coordinator

    It validates with the project's own command, lands as the project allows, and checks the result on the remote.

  9. Report coordinator → owner

    It tells you what changed and why, cites work as #<number> <slug>, and says what it did not check.

With the sandbox on

A sandboxed subagent cannot write the wrkslots registry, so it replies with its handoff instead, and the coordinator removes the slot after agentctl stop once its time-to-live has passed.

The harness directory

Setup turns the checkout you started in into the harness root and moves the checkout inside it, unchanged. For a repository foobar:

~/work/foobar/                  harness root; the coordinator runs here
├── AGENTS.md                   you are the coordinator; layout, tools, delegation,
│                               suite configuration, and your project rules
├── foobar/                     primary checkout, an independent repository
├── agent-utils/                clone, submodule, or symlink to an existing checkout
│   ├── bin/                    tool dispatchers; Rust edition by default, built through Cargo
│   └── skills/
├── worktrees/                  wrkslots control directory
│   ├── slots/<slot>/           one checkout (or disk image) per task
│   └── wrkslots                the wrkslots command for this harness
├── bin/agent-liveness          exit 0 dead, 1 alive, 2 unverifiable
├── .agents/skills/             links into agent-utils/skills/
├── .claude/skills -> ../.agents/skills
├── .agentctl/                  session registry and launch profiles; private
└── .wrkslots.yml               slot policy, commented key by key

The project folder has its own Git history for configuration and skill links. Checkouts, worktrees, session state and chat credentials stay outside that history. agentctl requires .agentctl/ to be ignored.

Updating agent-utils also updates the linked skills. Most tools with two editions default to Rust and build on first use, so cargo must be on PATH, including in timer services. Set AGENT_UTILS_ENGINE=python to use Python.

How you stay in the loop

One voice

The coordinator gathers subagent reports and tells you what changed, why and how it was tested.

References you can follow

Reports link to the work and its tests. Published comments and commit bodies identify the agent that wrote them.

Eyes on every agent

Attach to an interactive agent in Herdr or tmux. Read along, or pause automation and type.

Policy stays yours

Ask the coordinator to change agent settings or project instructions. You control which commands herdr-run allows.

Limits

  • Linux only. wrkslots, dagrun and the slot limits need systemd and cgroup v2. agent-usage also runs on macOS.
  • Not a security boundary. The slot sandbox and the herdr-run allowlist stop accidents by cooperative agents, not a hostile one.
  • Ready is not done. agentctl knows when an agent is waiting for input; only the agent's reply says the task is finished.
  • Herdr is installed separately. agentctl also supports tmux panes and headless workers.
  • Two chat providers. Slack, through the event-driven bridge and a Slack command-line client, and Google Chat, polled.
  • Pre-1.0. agentctl is beta.
